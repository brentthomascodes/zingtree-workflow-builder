The single most common button label in the whole tree was the literal text .btn-careful.btn-red — a CSS selector typed into the visible label field, on all 16 "Urgent" and "Scheduling Note" continue buttons. Relabeled to "Acknowledge & Continue" or "Continue."

Script-driven Ear & Nose (this pass)

The first pass (above) touched styling and cleanup only. This pass changes structure: the Ear and Nose branches relied on a long chain of single-purpose Content nodes to collect a handful of related answers one at a time. Each chain is now one intake screen (native form fields, follow-ups shown only when relevant) → one script that evaluates the answers → one router that jumps to the same outcome nodes the old chain used to land on. Every outcome, alert, and instructional screen downstream is untouched — only the question-collecting nodes in front of them were replaced.

Net

116 → 98 nodes

A 15.5% reduction tree-wide, and an 80%/67% reduction within the two converted branches specifically. Throat, Other, and Established Patient are unchanged this pass — see note below.

Validated before writing any new JSON: both branches' original decision logic was replayed against an executable model of the source tree's actual button links (30 Ear test cases, 15 Nose test cases, 100% match) before either script was written, and the assembled tree was checked for broken links, orphans, and unreachable nodes after assembly.

3dead branches

Vestigial questions found and folded in

Three original questions had both (or all) of their answers lead to the exact same node — a real inefficiency in the pre-existing tree, surfaced by this consolidation rather than caused by it: node 6 "Otorrhea, Hearing Loss?" (reached from Pain), node 39 "Nasal Trauma?", and node 27's entire "Associated Sinonasal Symptoms?" sub-tree. Those questions are no longer asked at all — the new script routes straight through.

2age fields

Numeric age replaces age-bracket buttons

The original tree asked staff to pick a bracket ("<18" / ">18 but <65" / ">65") — a judgment call at the boundary. The new intake asks for the patient's actual age and applies a fixed rule (65 and older, 18 and older) at those same boundaries. Flag if the practice wants different boundary behavior.

2branches

Left unconverted this pass

Throat, Other, and the Established Patient cluster (161/138/139/95/etc.) still use the original Content-chain pattern. Established Patient's sub-menus are genuine live staff decisions rather than data-driven branching, so converting them has little payoff for the risk of a larger unreviewed rewrite. Throat/Other are good candidates for the same treatment in a follow-up pass, pending a look at this one first.

ETL follow-up: content nodes should render dynamic data

Direct correction from Brent: think of every workflow as Extract → Transform → Load, and treat "the same variable set from multiple content nodes" as a signal to consolidate further — even past the initial intake/router, into the outcome nodes themselves. Captured as a permanent house rule in the Zingtree Builder workspace's MEMORY.md. Two concrete fixes applied here:

Before — 3 static nodes, 1 dead question

Nodes 135 "Adult CI Protocol" and 147 "Pediatric CI Protocol" held byte-identical instructions. The only reason both existed was an age question whose sole job was picking between two nodes that said the same thing.

After — 1 node, 0 questions

Node 147 deleted; 135 renamed "Cochlear Implant Coordinator Referral" and now serves both ages. The age question is gone from the intake screen entirely — it was never actually used for routing.

Before — 4 nodes, 2 more questions

The "not actively bleeding" epistaxis path asked "Is the nose packed?" (179) and "Blood thinners?" (180) as two MORE single-purpose screens, then landed on one of two scheduling notes (181, 182) that differed only in a day range ("5 and 10" vs "3 and 7").

After — 0 nodes, computed inline

Both questions moved onto the Nose intake screen as native conditional fields. The script now stages the day-range paragraph as ${transforms.nose_day_range_html}, and node 188 renders it directly — 179, 180, 181, and 182 are gone.

Both fixes were audited against every OTHER caller before touching anything: nodes 135/136 are also reachable from node 98 (a different, untouched branch) — only 135 gained a second caller, nothing about that path changed. Nodes 179/180/181/182/188 have no callers anywhere outside the Nose epistaxis chain. merge_vars_not_fixed is now set tree-wide, required the moment any node renders ${transforms.x} and might be revisited.

Net this pass: 98 → 93 nodes. Still open, deferred pending a full audit of their other callers (Throat/Other/Established Patient/node 77 Physician Triage): whether the genuinely shared provider-group nodes (55, 56, 60, 61, 62, 66) warrant the same dynamic-content treatment.

All 57 land on the same node and show the same alert card. A separate check confirms no path can render an empty alert or notice.

13 more buttons had the literal CSS class .btn-blue typed into their visible label (6 on node 5, 7 on node 116), plus *…* emphasis markers that render literally. 2dead questions

113 and 114 never changed anything

"Face Lump/Lesion" (On the Skin / Under the Skin) and "Mouth Lump/Lesion" (Lip, Tongue, Jaw, or Cheek / Tonsil or Palate) each had both answers leading to node 59. Five dead questions have now turned up across the whole redesign. Node 116 "Aesthetic Concern" was a related case: 7 of its 9 buttons led to the identical node.

Still a spider web, deliberately left for its own pass: node 77 "Physician Triage" (17 buttons — arguably a legitimate staff pick-list rather than a decision), node 98 "Automatic Complex" (11), node 4 "Throat" (8), and the Established Patient cluster. The biggest remaining prize is the 15 shared provider-group nodes — one static node each, all the same shape — but they are reached from every branch in the tree, so collapsing them into one dynamic screen is the highest-risk change left and needs its own inbound audit.
