What each type is:
Content — agent-facing screens: instructions, forms, rendered Dynamic HTML, and the failure/retry screens.
Logic — routing nodes (the export JSON calls this type scoring, a legacy name). Each button carries one boolean expression and routes on it — here that's the API health-checks reading _zt_meta.response.code, loop continuations like is_more_child_tickets == true, and selection guards. No computation happens in these; scripts set the flags they read.
Script — JavaScript nodes: build payloads, group PNRs, render HTML, advance loop cursors, set the flags the Logic nodes route on.
API call (DCO) — the export's data type: nodes that fire a Connected Object (the DCO), i.e. the actual outbound API request to Edvin or Zendesk via CX Actions, with the response landing in actions.<alias>. These are the 10 calls section 3 proposes logging.
Tree link — a jump to another workflow (open_tree_id + return node), not the workflow itself: Register Errands' single tree-link node is node 76 handing off to the VI workflow, and VI's is the return jump back.

2. What the raw types hide: this is mostly one repeating unit

Per the tree's own claude.md changelog (v42, 2026-08-25), all 10 API-call (DCO) nodes were wired into an identical pattern: every API call gets a paired Logic node that reads _zt_meta.response.code, and a paired Content node for the failure path. That single pattern accounts for 10 of 10 API-call nodes, 10 of 20 Logic nodes, and 10 of 28 Content nodes — over a third of the entire tree exists to call an API and handle it not answering.

3. When it's worth sending this to Datadog (or similar)

Zingtree already logs Connected Object requests/responses and script errors — but only in Execution Insights, one session at a time, with no cross-session aggregation, no alerting, and (per the troubleshooting reference) it's explicitly a debugging console, not an operations one. That was the right tool while this tree was being built. It stops being enough the moment the question changes from "why did this one session fail?" to "is Edvin degraded for everyone right now?" — which is exactly the question that matters now that this workflow went live to ~2,500 agents (go-live 2026-08-26, per the CR-015 pre-launch review).

The mechanism

Zingtree has no native "ship logs to a 3rd party" setting. The only path out is the same one this tree already uses for Edvin/Zendesk: add one more Connected Object (a Universal/HTTP connector against Datadog's Log or Metrics intake API, API-key auth) and fire it as an API-call (DCO) node from the spots below. CX Actions is already a licensed feature on this account, so this is an incremental Connected Object, not new platform capability.

Volume trade-off: logging every one of the 10 API calls on both success and failure roughly doubles the outbound calls this tree makes per session. Recommend logging failures and retries unconditionally (that's the actionable, alertable case and the volume is naturally low) and treating successes as a sampled or count-only metric rather than a full log line, so the added Connected Object doesn't add noticeable latency to the common path for 2,500 agents.
Data-handling note: a couple of these payloads (the raw API response dump, PNR/session identifiers) carry customer and booking data. Per how this account already gates similar changes (see the ETG approval queue's "nothing touching auth/payments/PII ships without human review" rule), scope the Datadog payload to identifiers and status metadata — node id, alias, response code, session id, tag — rather than full passenger/contact fields, and treat the Connected Object itself as something worth a quick data-handling review before it ships, since it's new data leaving Zendesk/Zingtree for a third-party vendor.
