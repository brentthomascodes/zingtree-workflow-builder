## 1. Business context & outcome
This tree verifies a GIC customer's order, resolves or creates the Salesforce Case for it, and seeds that case with order/product/contact data so the downstream Case Type Routing Tree can classify it (return, cancellation, order edit, etc.). The current production version intermittently fails with Zingtree's "invalid loop" runtime error — confirmed in GIC's own 2026-08-26 bi-weekly testing notes ("a production-relevant invalid loop error in order verification... case still creates despite the error"). The metric that matters here is reliability: the case gets created either way today, but the agent-facing session breaks, and (per the same note) this may already be affecting production, not just UAT.

## 2. Actors & journey
- **Who uses it** — GIC support agents, inside the agent console (Salesforce-embedded Zingtree session).
- **Where it runs** — GIC's Zingtree org (605610), launched from an existing Case or a fresh session, reading inbound `sf_*` predefined vars.
- **Journey** — agent opens the tree → confirms session/case validity → collects the reason for contact and any order/case identifiers already known → resolves the order (by number or by search) → checks for existing cases on that order → merges into one, updates one, or creates a new case → (new case only) waits for the case's GTK key to populate → reviews and adds order line items to the case → adds a verification comment → hands off to Case Type Routing.

## 3. Scope
**In scope**
- Full rearchitecture of the tree per ETL/best-practice conventions (`zingtree-workflow-builder` skill), preserving all business logic and data contracts.
- Diagnosing and fixing the invalid-loop-guard risk Brent flagged (line-item loop) plus two structurally identical risks found during the rebuild (GTK-key wait, product-availability wait).
- Consolidating duplicate/redundant screens and scripts found in the baseline (multiple copies of the same intake screen, existing-case screen, US/CA division logic, etc.).
- Fixing bugs found during the rebuild (see §4, R5–R7).
- Producing a new tree JSON, not modifying/importing over the live tree.

**Out of scope (this round)**
- Actually importing the new JSON into Zingtree or publishing it live — that's Brent's own testing and approval step, never automated (CLAUDE.md standing rule).
- Reconfiguring any Connected Object (CX Action) body template server-side — none were changed; the rebuild works within the existing DCO configuration.
- Deciding whether GIC's Salesforce side can accept a single batched line-item insert instead of one call per item (flagged as a follow-up in §9, needs Arun/Vamshi — an account-side API decision, not something this rebuild can make unilaterally).
- The Case Type Routing Tree itself — out of scope, this tree only hands off to it.

## 4. Functional requirements

### R1 — Bound the line-item loop with a real agent-click checkpoint · **Must**
- **Source:** "If we ever get into a case where we've selected an order with many order line items, I believe that would trigger an invalid loop here. Check for that. If that's the case, we need to add a content node for an agent to manually say, 'Add this order line item, add this order line item.' We want to display what those details are." — Brent, direct, 2026-09-09
- **Requirement:** Confirmed. The baseline advances the line-item-add loop (nodes 79/80/81/107) with a 1-second `escalate_after` auto-continue and no real agent interaction between items — the exact shape Zingtree's ~30-programmatic-jump invalid-loop guard exists to stop, and it matches GIC's own 2026-08-26 production report. The rebuilt loop (`cursor_next_line_item` → `add_case_product` → `grade_case_product` → `route_more_line_items`) forces a real, un-timed agent click (`screen_checkpoint`, no `escalate_after`) at least once every 10 line items, regardless of order size.
- **AC-1.1** — Given an order with 45 selected line items, when the agent works through the review screen, then the walked path shows a genuine agent-click checkpoint after every 10th item (4 checkpoints for 45 items) and never more than ~4 automatic node hops per item in between.
- **AC-1.2** — Given an order with 5 line items (fewer than one checkpoint's worth), when the loop runs, then it completes without ever hitting a checkpoint screen.
- **Notes / open items:** Verified via `scripts/walk.mjs` against `fixtures/new_case_45_line_items.fixture.json` — 45 items, path length 221 steps, 4 checkpoint hits, terminates cleanly. See §11.

### R2 — Remove the other two auto-advancing "wait and recheck" loops · **Must**
- **Source:** Brent, direct, 2026-09-09 — "these loops are broken, and this workflow is very fragile."
- **Requirement:** The baseline has two more instances of the same anti-pattern found under R1: the GTK-key wait (nodes 120/121/118, a 3-pass counted retry with a `transforms.breakloop` counter) and the products-availability wait (nodes 139/140/149/150/151). Both are replaced with a single wait screen and a single re-check — no loop-back edge, no counter.
- **AC-2.1** — Given a new case whose GTK key hasn't populated yet, when the single re-check finds it still empty, then the agent sees a non-blocking heads-up screen (`screen_gtk_key_missing`) and can continue rather than being silently looped or silently proceeded past.
- **AC-2.2** — Given the products-availability wait, when case products are needed for the line-item de-dup check, then they are fetched once, synchronously, as part of building the line-item queue — no separate poll.
- **Notes / open items:** none.

### R3 — Consolidate duplicate screens and scripts, top-down ETL structure · **Must**
- **Source:** Brent, direct, 2026-09-09 — "Look to implement best practices from an ETL perspective here. We want to work top down."
- **Requirement:** Rebuild the tree per `zingtree-workflow-builder`'s ETL conventions: Extract → Transform → Load per section, one screen per genuinely distinct question, one script per genuinely distinct computation, form-data-first namespacing. Baseline duplicates removed: two byte-identical intake screens (nodes 1/127) → one (`screen_intake`); three near-identical existing-case screens (61/86/111) → one (`screen_existing_cases`); four independent copies of the same US/CA division fallback logic (nodes 40/58/70/71) → one (`route_intake` / `seed_criteria_search`); two overlapping summary+comment screens → one each on the merge, update and new-case paths.
- **AC-3.1** — Given the rebuilt tree, when it's linted (`scripts/lint_tree.py`), then no node violates "never two of the same node type back-to-back" without a documented exception, and no duplicate screen/script pair remains.
- **AC-3.2** — 101 baseline nodes → 67 in the rebuild, with the removed nodes accounted for in the tree-diff report (consolidation or confirmed dead code — see R8).
- **Notes / open items:** none.

### R4 — Case Type Routing handoff on every case-touching path · **Must (behavior change — flagged for confirmation)**
- **Source:** Brent, direct, 2026-09-09 — "organize that data as a type of case and seed it with data. That way, when the other workflow, the case type routing workflow, picks it up, it will correctly identify a return, a cancellation, an order edit, or whatever it is."
- **Requirement:** Tracing the baseline's actual wiring (not just its node labels) found it only reaches the Case Type Routing tree-open node (baseline node 115, `open_tree_id = 1`) from **one of four** case-touching end states — case-create-found-an-existing-record. Explicit merge (node 92), explicit update (node 62), and even a clean brand-new case (node 63) all dead-end with no continuation at all in the baseline. That contradicts the stated purpose of this tree. The rebuild sends every case-touching path (create, merge, update) through `goto_case_type_routing`.
- **AC-4.1** — Given a merge into an existing case, when the merge completes, then the session re-reads that case's type (`fetch_case_type_after_merge`, reusing DCO 221) and hands off to Case Type Routing.
- **AC-4.2** — Given an explicit update to a selected case, when the update completes, then the session hands off to Case Type Routing (already true in the baseline for this path's near-neighbor; now made explicit and consistent).
- **AC-4.3** — Given a brand-new case creation, when line items and the verification comment are added, then the session hands off to Case Type Routing.
- **Notes / open items:** **This is a genuine behavior change from the literal baseline, not a faithful port** — flagged as OPEN ITEM in §9 (Q1) because it rests on inferring intent from an inconsistent baseline. Also OPEN: whether tree ID `1` is really Case Type Routing — it's the baseline's only wired value, but suspiciously low next to this org's other tree IDs (this tree is 411323165). The tree-open node baseline literally labeled "Case Type Routing Tree" (node 41) had `open_tree_id = 0` and zero predecessors — unreachable, likely an earlier abandoned attempt at this same handoff.

### R5 — Bug fix: Last_Name__c field mapping · **Must**
- **Source:** Found during rebuild (not requested; flagging per org code-review policy).
- **Requirement:** Baseline node 89 wrote `caller_first_name` into **both** `First_Name__c` and `Last_Name__c` when staging a case-merge payload (copy/paste error). Fixed in `prep_case_merge` to use `caller_last_name` for `Last_Name__c`.
- **AC-5.1** — Given a merge payload is staged, when `transforms.Last_Name__c` is set, then its value comes from `caller_last_name`, not `caller_first_name`.
- **Notes / open items:** This means every case merged through the live baseline today has been writing the caller's first name into the Salesforce `Last_Name__c` field. Worth a data-quality check on existing merged cases if that's material to GIC's reporting.

### R6 — Bug fix: duplicate DCO 223 call on the known-order-key path · **Must**
- **Source:** Found during rebuild's own self-review (see change log below — this was introduced and then caught within this rebuild, not inherited from the baseline).
- **Requirement:** An earlier pass of this rebuild bundled DCO 223 (`get_cases_with_same_order`) into both search entry points, which — unlike the baseline, where the known-key path never reconverges with the criteria-search path's own 223 call — would have made the rebuild call it twice back-to-back for the single most common case (an agent typing in an order number that matches exactly one order). Fixed: 223 is now called from exactly one node (`fetch_cases_for_order`), reached by both entry points.
- **AC-6.1** — Given a known-order-key search that matches exactly one order, when the session proceeds to check for existing cases, then DCO 223 is called exactly once. Verified via `scripts/walk.mjs` (`get_cases_with_same_order` called `1x` in both the stress-test and merge fixtures).
- **Notes / open items:** none.

### R7 — Failure handling for case create and GTK-key wait · **Should**
- **Source:** Found during rebuild; the baseline had no explicit failure branch for either.
- **Requirement:** A failed case-create call is now surfaced to the agent (`route_case_create` → `screen_case_create_failed`, rendering the Connected Object's error body) instead of silently continuing into the line-item loop with no case. A GTK key that never populates is surfaced as a non-blocking heads-up (`route_gtk_key` → `screen_gtk_key_missing`) rather than silently looped on or silently proceeded past.
- **AC-7.1** — Given DCO 609 (case create) returns a non-2xx response, when the session grades that response, then it routes to `screen_case_create_failed` and never reaches the line-item loop or GTK-key wait. Verified via `scripts/walk.mjs` against `fixtures/case_create_failure.fixture.json`.
- **Notes / open items:** none.

## 7. Edge cases & failure modes
- **Order search returns 0 / 1 / many results** → `screen_no_orders` (search again) / auto-resolved / `screen_select_order` (grid).
- **No products on the resolved order** → `screen_no_products`, agent can choose a different order.
- **No contacts on the account** → `screen_no_contacts`, agent can proceed anyway (case created without a linked contact).
- **Case create fails (non-2xx)** → R7, `screen_case_create_failed` with the error body rendered, session does not proceed into the line-item loop.
- **GTK key never populates** → R2/R7, non-blocking heads-up, agent can continue.
- **Line item add fails for one item** → recorded on that item (`added: false`), loop continues, failure count shown on the summary screen before the comment step — the agent is not blocked but is told.
- **Order has many line items (the headline scenario)** → R1, bounded checkpoint loop, verified to 45 items.
- **Existing cases already open on this order** → agent chooses merge / update / create-anyway; all three now reach Case Type Routing (R4).
- **Zero session / closed case** → `gate_session` routes to `screen_case_closed` or `screen_no_session` before any data is touched.

## 8. Non-functional & compliance

Per Zingtree org policy and Anthropic-org code-review guidance, **a teammate should review the payload-building scripts (`prep_case_payload`, `prep_case_merge`, `prep_case_update`) before any live import** — flagged, not yet done.
- **Logging**: no `ZT.log` calls anywhere in the rebuild (house rule) — the baseline had several, all removed.
- **Environments**: built and tested offline only (lint + walk fixtures against the JSON export). Not yet imported into any Zingtree environment, sandbox or production.
- **Reversibility**: delivered as a new file, not an overwrite — the baseline JSON is preserved alongside it for comparison/rollback reference.
