## 4. Functional requirements — reconstructed baseline (current published behavior)

### R1 — Initial DOT classification `[inferred]` · **Must**
- **Source:** current tree, node 1 ("Incident Classification - DOT Check") + node 2 ("DOT vs Non-DOT Routing")
- **Requirement:** The agent answers three yes/no questions (major accident, aircraft destroyed, fatalities). If any is "Yes," the session routes immediately to a DOT alert screen (node 3) and then directly to the shared summary-build script (node 51) — **skipping the damage-assessment, Reasonable-Suspicion, and role/airport/OSM capture entirely.**
- **AC-1.1** — Given any of the three DOT-check questions is "Yes," when the agent continues, then the session reaches node 3 ("DOT Incident — Stop and Call Delta") without passing through nodes 7–15 or 46–50.
- **Notes:** field name `sf_Specimen_Requested__c` is used to hold the "major accident?" answer — a label/field mismatch, not a behavior bug; left as-is per §3 out-of-scope.

### R2 — Branch fork: Reasonable Suspicion vs Accident `[inferred]` · **Must**
- **Source:** node 46 ("Is Suspicion?")
- **Requirement:** When node 2's DOT check is "No" on all three questions, the session checks `sf_Event_Type == "Suspicion"`. Suspicion → node 47 (suspicion reasoning capture). Anything else → node 7 (no-testing factor assessment, accident branch).
- **AC-2.1** — Given `sf_Event_Type == "Suspicion"` and no DOT-check flag is "Yes," when the agent continues past node 2, then the session reaches node 47.

### R3 — Accident branch: no-testing exemption check `[inferred]` · **Must**

- **Requirement:** Four yes/no questions (minor/cosmetic damage, mechanical/equipment fault, weather, >32h elapsed) gate a "No Testing Required" screen when all four match the exemption pattern; otherwise the flow proceeds to damage-type assessment (node 38).
- **AC-3.1** — Given all four no-testing conditions are met, when the agent continues, then the session reaches node 9 and then node 32 without visiting the damage-type loop.

### R4 — Accident branch: damage-type assessment + testing determination `[inferred]` · **Must**
- **Source:** nodes 38, 40–45, 10, 42–44, 11
- **Requirement:** The agent selects one or more damage types (Aircraft, GSE, Vehicles, Property/Structure, Injuries, Flight Delay) in a repeatable loop; each iteration asks type-specific follow-up questions and stores a record (`transforms.final_records`). After the loop, node 11 evaluates: no-testing exemptions → medical-care deferral (injury + seeking care) → qualifying-damage testing determination, including a "drug test only, no alcohol" note when `hours_elapsed` (asked only when >32h == "No") is between 8 and 32.
- **AC-4.1** — Given `sf_Personal_Injury__c == "Yes"` and `injury_medical_care == "Yes - Seeking Medical Care"` on any record, when node 11 runs, then `testing_classification == "DEFERRED"` regardless of other records.
- **AC-4.2** — Given `hours_elapsed` between 8 and 32 and at least one qualifying damage type, when node 11 runs, then the summary includes the drug-only timing notice.

## 7. Edge cases & failure modes (reconstructed baseline, relevant to CR-001)

- **Immediate-DOT shortcut skips input capture entirely** — when node 2 routes straight to node 3→51, `employee_role`/`sf_Airport_Code__c`/`sf_Member_ID_Number__c`/`sf_Internal_Notes__c` have never been asked. Node 51 and the final summary render them as blank/"Not answered." This is the most severe instance of the ordering problem CR-001 fixes — see R16.
- Airport code not in `supportedAirports` → a "review manually" note is added to `teamNotes`; session continues (not blocking).
- No qualifying damage type across any record → `testing_classification = 'NON_DOT_NO_TESTING'`, still reaches the same summary/email path.
- Multiple damage-type records with conflicting fault/medical-care answers → node 11 evaluates `records[0]` for `hours_elapsed`/fault (incident-level assumption) but loops all records for qualifying-damage detection — an existing assumption, not touched by CR-001.
- `employee_role` values that match neither the DOT list nor "Work From Home Employee" nor "Other" cannot occur (native `select` is a closed list) — no fallback needed.
- WFH + an accident flag both true (a work-from-home employee also marked as having caused/witnessed a major accident): under the canonical rule (CR-001 R13), `isDot` and `isWFH` can both be true simultaneously; `hotlineRequired` is true either way, but which messaging block displays (DOT vs WFH wording) depends on evaluation order — **flagged as an assumption in §10**, not blocking.

Node 19 reads the classification producers' output like this:
```
function g(k) { return ZT.getVariableValue(k, ''); }
const testingHtml = g('testing_summary_html').trim() || <fallback string>;
```
`ZT.getVariableValue()` only reads the **form-data** namespace.
