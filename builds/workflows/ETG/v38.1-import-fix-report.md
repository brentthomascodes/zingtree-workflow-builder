## Root cause

v38's build script dropped the now-unused `grandchild_parent_resolved` entry from
`predefined_vars` with a plain `delete pv["14"]` — which removes the key without
re-indexing anything after it. The two new entries added this session
(`grandchild_parent_blocked`, `should_skip_grandchild_create`) then landed at keys
`15` and `16` (computed from the highest existing key + 1, which no longer included
14). Net result: `predefined_vars` keys ran `0,1,2,...,13,15,16` — **missing 14**.

`validate_tree.js` never catches this class of defect: it only ever calls
`Object.values(tree.predefined_vars || {})` to check declared variable names, and
never looks at the keys themselves. So a key gap here is invisible to the offline
validator, but predefined_vars almost certainly follows the same contiguous-key
convention Zingtree enforces on `nodes` (`project_node_id`/`display_order` must equal
the dict key, no gaps) — which is the same class of "silent import failure" bug
this workspace's own house rules already warn about for nodes, just in a collection
the checklist hadn't previously needed to name explicitly.

Also found and fixed while in here (confirmed non-fatal, since v37 already had it
and imported fine, but a real deviation worth cleaning up): the two new
`predefined_vars` entries had `project_id` as a **string** (`"595124299"`, inherited
from the top-level `data.id` field, itself a string) where every original entry
(0-13) has it as a **number** (`595124299`). Normalized all entries to match the
proven number type.

## Fix

Re-indexed `predefined_vars` to a contiguous `0..15`, preserving insertion order
(so `should_skip_grandchild_create` — the only variable that's functionally new
in this file — still lands last). No node content changed at all; the diff between
v38 and v38.1 is `predefined_vars` only, confirmed programmatically.
