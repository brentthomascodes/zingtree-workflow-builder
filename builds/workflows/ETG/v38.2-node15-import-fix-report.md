None of that found anything wrong. So I did a **field-by-field diff of node 15

- `page_title`: `"Grandchild ticket already created?"` → `"Skip grandchild create?"`
- `buttons[0]`/`buttons[1]` `button_text`/`logic_expression`: the variable name
  `grandchild_ticket_already_created` → `should_skip_grandchild_create` (a
  brand-new flag, introduced this session, never previously imported)

Every structural field — `button_link` targets, `continuation_node_id`, `rank`,
`op`, `wizard_skip` — was byte-identical.

## Diagnosis

I can't fully explain *why* Zingtree's importer objects (I don't have documentation
on its internal validation, and the offline validator doesn't model it at all —
this is the second failure in a row it's missed entirely). But the diff makes the
actionable conclusion clear: the only things new about node 15 are a never-before-
imported variable name and a new predefined_vars entry for it. Rather than keep
guessing which specific part Zingtree's importer rejects, the safest fix is to
**not introduce anything new on the one node a real import failure is specifically
named against.**

## Fix

- **Node 15**: reverted to be **byte-identical to v37/v35** — unchanged since
  before this session's work. Still tests `grandchild_ticket_already_created`,
  same page_title, same everything.
- **`predefined_vars`**: reverted to be **byte-identical to v37** — nothing added,
  nothing removed (the now-unused `grandchild_parent_resolved` /
  `grandchild_parent_blocked` declarations are left as harmless dead entries
  rather than risk touching this collection again, given v38.1's key-gap bug
  already came from editing it).
- **Node 36**: keeps the behavioral improvement (skip instead of guess-and-create
  on a miss) by **overloading the existing, already-proven
  `grandchild_ticket_already_created` flag** — it's now `true` either when this
  grandchild was already attempted (the original v12 meaning) or when this pass's
  resolve came up blocked. Node 15 doesn't need to know which, and doesn't need to
  change at all. `grandchild_parent_blocked` is now a plain local JS variable
  inside node 36 — not form data, not a predefined_var, nothing outside that node
  reads it.
- **Nodes 10/29**: dropped the now-unnecessary `grandchild_parent_blocked` form-data
  reset (it's no longer form data).
- **Node 39**: reverted to its exact v37 body (was already close; kept as-is to
  minimize deviation from the last proven import).

Net diff from v37: **nodes 10, 29, 36, 40, 41 changed; the 10 gate nodes removed;
nodes 15, 21, 39, and `predefined_vars` are completely unchanged.**
